# DSC---ATS-Signing-Utility
Windows desktop app and local agent to digitally sign PDFs and offer letters with a USB DSC token (PKCS#11). Vendor-neutral. Java, PDFBox, BouncyCastle.
# ATS Signing Utility

A Windows desktop program and a local signing agent that sign PDFs (for example offer letters generated by the ATS) with a **USB DSC token**, like the greytHR signature utility.

- **Desktop app (`ATS Signer.exe`)**: open a PDF, drag a box where the signature should appear, sign it, sign a whole folder at once, and verify signed PDFs.
- **Local agent (`127.0.0.1:8765`)**: lets the ATS web app ask the HR user's PC to sign a document with the token.
- **Vendor neutral**: it talks to the token through the vendor's PKCS#11 driver (a `.dll`). A different DSC vendor means a different driver path, not new code.

> **Status:** the desktop app and the agent are built and tested with a test certificate (`.p12`). Tests with a real USB token and the ATS backend integration are the next milestones (see [Status and roadmap](#status-and-roadmap)).

## Why a local program

A DSC private key lives inside the USB token and can never be exported. A web page (JavaScript) cannot reach USB devices or the token driver. So signing must happen on the PC where the token is plugged in.

```
 Browser (ATS page)  --HTTP-->  Local agent on the HR PC  --PKCS#11-->  DSC token
 (cannot reach USB)             127.0.0.1:8765                          (key never leaves)
```

## How it works

### Desktop signing (inside the app)

1. The user opens a PDF. PDFBox renders the page as an image.
2. The user drags a box. Pixels are converted to PDF points (scaled, Y axis flipped).
3. The PIN popup appears. The signer opens the token (or the test file) with the PIN.
4. PDFBox reserves 16000 bytes for the signature and builds the visible box.
5. PDFBox gives the two byte ranges of the document. A SHA-256 hash is signed inside the token and a CMS/PKCS#7 detached signature (`adbe.pkcs7.detached`) is built with BouncyCastle.
6. PDFBox writes the CMS into the PDF with an incremental save to a **new file**. The original is never changed.
7. The program logs out of the token and wipes the PIN.

### ATS web app flow (agent)

1. HR clicks **Sign** in the ATS.
2. The ATS backend prepares the PDF with an empty signature placeholder and the bytes to sign.
3. The page posts the bytes (Base64) to `http://127.0.0.1:8765/v1/sign`.
4. The agent checks origin, host and headers, shows the PIN popup with the document label and SHA-256, signs in the token, and returns the CMS.
5. The ATS backend verifies the CMS, checks that the certificate serial belongs to the user, inserts it into the PDF and stores the file with an audit record.

## Quick start (development, no token)

1. **Build the jar:** `build.bat`, or in IntelliJ: Maven, Lifecycle, `clean` then `package`. The result is `target/ats-signing-agent.jar`.
2. **Create the test certificate:** run `make-dev-cert.bat`. It creates `dev-signer.p12`. The password (the "PIN") is `changeit`.
3. **Start the desktop app:** run `SignerApp` in IntelliJ, or `run-utility.bat`.
4. **Or start the agent only:** `run-console.bat` (shows the log) or `run.bat`. It listens on `127.0.0.1:8765`.

Test the agent from PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/v1/health
$body = '{"contentBase64":"aGVsbG8=","documentLabel":"test"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8765/v1/sign `
  -ContentType 'application/json' -Headers @{ 'X-ATS-Agent' = '1' } -Body $body
```

A popup asks for the PIN (`changeit`) and the reply contains a `cms` value.

## Using the desktop app

**Sign one PDF**
1. **Open PDF…**, choose a file.
2. Drag a box on the page where the signature should appear (a click puts a default box at the bottom right).
3. Optionally fill **Reason** and **Location**.
4. **Sign…**, type the PIN, choose where to save. The signed copy is a new file.

**Bulk sign**
1. **Bulk sign…**
2. Choose the PDF folder and the output folder.
3. Choose the page (last, first or a number) and one of 7 positions.
4. Optionally type a reason. Click **Start signing** and enter the PIN once.
5. Signed files are saved as `name_signed.pdf`. Existing signed copies are skipped. A CSV report is saved in the output folder.

**Verify** opens a signed PDF and reports whether it is intact, who signed, and the certificate details.

**Signer settings…** chooses the signer: test certificate file, DSC token (PKCS#11 driver, or automatic), and the optional slot. Settings are saved per user in `C:\Users\<you>\.ats-signing-utility.properties`.

**Connected device** (second row) shows the token name. It refreshes at startup, when you come back to the window, after changing settings, and on **Refresh**.

## Using a real DSC token

1. Install the vendor driver (for example ePass2003, WatchData ProxKey, a CA-supplied one). Use the 64-bit version to match 64-bit Java.
2. Plug in the token.
3. In the app: **Signer settings…**, choose the DSC token option. Leave the driver on automatic, or **Browse** to the driver `.dll`.
4. Click **Refresh**. The device name should appear with a green dot.
5. List the certificates on the token without signing: run `token-check.bat` (it asks for the PIN in the console).
6. For the agent, edit `agent.properties`:
   ```properties
   signer.type=pkcs11
   pkcs11.libraries=C:/Windows/System32/eps2003csp11.dll
   ```
   Use **forward slashes**. Backslashes break `Properties` files.

Common driver files: `eps2003csp11.dll` (Feitian ePass2003), `SignatureP11.dll` (various), `wdpkcs.dll` (WatchData), `eTPKCS11.dll` (SafeNet).

**PIN safety:** after a few wrong PINs the token locks and only the vendor's unlock tool or the CA can reopen it. The program stops at the first wrong PIN and never retries on other slots. The user PIN is changed with the vendor's token manager, not with this program.

## Build the .exe

```
package-exe.bat
```

Result: `dist\ATS Signer\ATS Signer.exe`. Zip the **whole folder** and give it to users. No Java installation is needed on their PC. Each HR PC still needs the vendor token driver.

If Maven is not on the PATH, build the jar in IntelliJ first (Lifecycle, `clean`, `package`). `package-exe.bat` then uses `target\ats-signing-agent.jar`.

Manual commands:

```
copy /y target\ats-signing-agent.jar jp-input\
jpackage --type app-image --name "ATS Signer" --app-version 1.0.0 --input jp-input --main-jar ats-signing-agent.jar --main-class com.ats.signingagent.desktop.SignerApp --dest dist --jlink-options "--strip-debug --no-man-pages --no-header-files" --add-modules java.base,java.desktop,java.naming,java.logging,java.xml,java.sql,java.smartcardio,jdk.crypto.cryptoki,jdk.crypto.ec,jdk.crypto.mscapi,jdk.httpserver,jdk.unsupported
```

Notes:
- `--jlink-options` keeps `java.exe` inside the program. Token auto-detection uses a helper process and needs it.
- `java.smartcardio` is needed for the connected device name.
- Add an `app.ico` next to `package-exe.bat` for a custom icon.
- Setup installer: install WiX 3.x and run `package-exe.bat installer`.
- Windows SmartScreen shows "unknown publisher" for an unsigned `.exe`. Click More info, then Run anyway. A code-signing certificate removes the warning.

More details: `docs/EXE_AND_UI_GUIDE.md`.

## Agent configuration

File: `agent.properties` (use forward slashes in paths).

| Key | Meaning | Default |
|---|---|---|
| `port` | Local port | `8765` |
| `allowed.origins` | ATS web addresses allowed to call the agent (scheme, host, port; comma separated) | `http://localhost:3000,http://localhost:8080` |
| `dev.allow.no.origin` | Allow calls without Origin (curl, PowerShell). **Set `false` in production.** | `true` |
| `signer.type` | `pkcs12`, `pkcs11`, `windows-store`, `custom` | `pkcs12` |
| `pkcs12.file` | Test certificate file | `dev-signer.p12` |
| `pkcs11.libraries` | Vendor driver path(s), first one that loads is used | none |
| `pkcs11.slotListIndex` | Slot to use if several tokens or readers | automatic |
| `allowed.issuers` | Only offer certificates whose issuer contains one of these texts | none |
| `max.content.mb` | Largest request accepted | `20` |
| `signer.class` | Class name for `signer.type=custom` | none |
| `pin.source` | `dialog` (popup) or `env` (tests only, with pkcs12) | `dialog` |

Logs: `C:\Users\<you>\.ats-signing-agent\agent-%g.log`. PINs are never logged.

## Agent API

Base address: `http://127.0.0.1:8765`. Errors look like `{"error":"CODE","message":"..."}`.

### GET /v1/health
Returns `status`, `version`, `apiVersion`, `signerType`, `modes` and `busy`. The ATS uses it to detect that the agent is installed.

### POST /v1/sign
Headers: `Content-Type: application/json` and `X-ATS-Agent: 1`. The browser must send an allowed `Origin`.

```json
{
  "contentBase64": "<bytes to sign, Base64>",
  "documentLabel": "Offer 123 - A. Candidate",
  "expectedSerialHex": "9F099E8FB7EFD6F3"
}
```

`documentLabel` and `expectedSerialHex` are optional. If `expectedSerialHex` (the serial of the DSC registered to the logged-in user) is set, the agent signs only with that certificate.

Reply:

```json
{ "cms": "<Base64 detached CMS>", "sha256": "...", "signerSubject": "...", "issuer": "...",
  "serialHex": "...", "signerType": "pkcs11", "signedAt": "..." }
```

`signerSubject`, `issuer` and `serialHex` are for display. **The ATS backend must read these from the certificate inside the CMS and verify the signature itself.** Never trust values sent by the browser.

| Code | HTTP | Meaning |
|---|---|---|
| ORIGIN_NOT_ALLOWED | 403 | Page is not in `allowed.origins` |
| BAD_HOST | 403 | Host header is not localhost or 127.0.0.1 with the agent port |
| MISSING_HEADER / BAD_CONTENT_TYPE | 400 / 415 | Send `X-ATS-Agent: 1` and JSON |
| BAD_REQUEST | 400 | Body or Base64 is invalid |
| TOO_LARGE | 413 | Larger than `max.content.mb` |
| CANCELLED | 400 | The person closed the popup |
| WRONG_PIN | 401 | Wrong PIN. Do not retry blindly |
| TOKEN_LOCKED | 423 | PIN locked. Use the vendor's unblock tool |
| SIGNER_UNAVAILABLE | 503 | Driver not found, token not plugged in, or store not available |
| NO_USABLE_CERT | 409 | No certificate that is valid, allowed to sign and from an allowed issuer |
| EXPECTED_CERT_NOT_FOUND | 409 | The registered certificate is not on this token |
| BUSY | 429 | A signing popup is already open |

## Calling the agent from the ATS

```javascript
const res = await fetch('http://127.0.0.1:8765/v1/sign', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-ATS-Agent': '1' },
  body: JSON.stringify({ contentBase64, documentLabel, expectedSerialHex })
});
const data = await res.json();   // { cms, serialHex, ... } or { error, message }
```

Backend steps with PDFBox (external signing):

1. **Prepare:** load the offer letter, add a signature field and placeholder, compute the bytes to sign, store the pending request, return the bytes (Base64).
2. **Complete:** receive the CMS, **verify it** against the stored bytes, read the signer certificate, check its serial belongs to the user, insert the CMS, save the PDF, write an audit record.

Notes for the web team:
- Chrome 142 and later may show a **Local Network Access** permission prompt when a public https site calls `127.0.0.1`. The user allows it once.
- The agent must be running on the HR PC. Use `GET /v1/health` to detect it.
- Add a timestamp for long-term validity (see roadmap).

## Supporting another DSC vendor

All vendors ship a PKCS#11 driver. To support a new vendor:

1. Install the vendor's driver on the PC.
2. Find its driver file (check `C:\Windows\System32` and the vendor's folder).
3. Set it in **Signer settings…** (or `pkcs11.libraries` in `agent.properties`).
4. Run `token-check.bat` to list the certificates.

No code changes are needed. If a vendor has no PKCS#11 driver, implement `SignerBackend`, put your jar in `plugins/` and set `signer.type=custom` with `signer.class`.

## Security design

| Risk | Protection |
|---|---|
| Other computers calling the agent | Binds to `127.0.0.1` only |
| Any website calling it from the user's browser | Exact `Origin` allow-list |
| DNS rebinding | `Host` header must be localhost or 127.0.0.1 with the agent port |
| Simple cross-site requests | `X-ATS-Agent: 1` header plus JSON forces a CORS preflight |
| Silent signing | PIN popup every time, showing the document label and SHA-256 |
| Parallel misuse | Only one signing at a time |
| Large payloads | `max.content.mb` limit |
| Token lock-out | Stops at the first wrong PIN, no retries on other slots |
| PIN exposure | Never stored or logged; read as `char[]`, wiped after use; logout after each signing |
| Browser trust | Backend verifies the CMS and reads the signer from the certificate |

**Never commit** `.p12`, `.pfx`, `.jks`, PINs or real employee documents. The test password `changeit` is only for the throw-away test certificate.

## Troubleshooting

| Problem | Fix |
|---|---|
| `'mvn' is not recognized` | Build with IntelliJ Maven (Lifecycle, clean, package) or install Maven and add it to the PATH |
| `jpackage` says the main jar does not exist | Copy `target/ats-signing-agent.jar` into `jp-input\` first |
| Red dot: "No token detected" | Plug in the token, install its 64-bit driver, click **Refresh**, or choose the driver `.dll` in Signer settings |
| "Driver file not found" | Wrong path. Use forward slashes in `agent.properties` |
| Driver fails to load | 32-bit driver with 64-bit Java (or the reverse) |
| `WRONG_PIN` | Re-enter carefully. Too many wrong tries lock the token |
| `TOKEN_LOCKED` | Unlock with the vendor's tool or contact the CA |
| `ORIGIN_NOT_ALLOWED` | Add the ATS address to `allowed.origins` |
| Browser asks to allow local network access | Allow it (Chrome 142+) |
| Adobe shows "validity unknown" | Normal for a self-signed test certificate. A real DSC under the CCA hierarchy is trusted when the root is installed |
| Window opens and closes (`.exe`) | Add `--win-console` in `package-exe.bat` to see the error |
| Windows SmartScreen warning | More info, then Run anyway, or sign the `.exe` with a code-signing certificate |

## Status and roadmap

**Built and tested with the test certificate**
- Local agent API and all security checks
- CMS signing (self-checked) and verification with independent tools
- Desktop app: visible signature, bulk signing, verify, settings, device row
- Packaging to a standalone `ATS Signer.exe`

**Not yet tested**
- A real USB token through its vendor PKCS#11 driver
- The Windows certificate store signer
- Maven build on a clean machine
- ATS backend integration

**Planned**
1. Backend endpoints (prepare and complete) with server-side CMS verification and certificate chain and revocation checks.
2. RFC 3161 timestamp (PAdES-T), then long-term validation.
3. Map each DSC serial to an ATS user, plus audit tables.
4. Test with a real token, then with a second vendor.
5. Installer with `jpackage` and a code-signed `.exe`, plus auto-start for the agent.
6. Unit tests (sign then verify, tamper check, byte range).

**Known limits**
- Visible signatures on rotated pages are not supported.
- The visible box uses standard fonts, so non-Latin characters show as `?`.
- The signing time in the PDF is claimed by the signer until a timestamp is added.
- Trust (CA chain, revocation) is not checked by the built-in verifier.
